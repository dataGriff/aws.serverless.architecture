## Physical anchor, not a routing node

This page describes the physical bus. Routing is declared on the generated **logical channels**, one per event: `orders-bus.OrderPlaced.v1` routes here as `central-bus.OrderPlaced.v1`, which routes to each consuming domain's subscriber channel (`payments-sub.OrderPlaced.v1`). Those straight lines are what the visualiser draws; this page carries no `routes`, because a hub that routes back to every spoke is both the wrong model under ADR-021 and a shape EventCatalog 4.12.3 cannot render.

## How events get here and leave

- **In:** each domain bus's generated public-forward rule (`rules/{domain}-public-forward.json`), the single bus-to-bus hop EventBridge allows (Spike B: a second hop is refused with `THIRD_ACCOUNT_HOP_DETECTED`).
- **Out:** one generated **subscriber** per consuming domain per event (`subscribers/{domain}-{event}.json`): filter = the Classic consumer pattern, retry 185 attempts / 24 h, DLQ, delivered to the consumer's own queue or function. There is no fan-out to domain buses.
- **Archive:** a Firehose subscriber per domain validates and writes bronze (ADR-024).
