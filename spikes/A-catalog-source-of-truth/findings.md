# Spike A — findings

## Result
- [x] **go-with-changes.** An EventCatalog repo can be the single offline source from which routing patterns, subscribers, validation schemas, Parquet schemas, PII policy, ODCS contracts and the per-event channel pages are generated and checked; a catalog PR is the only way any of them change, and `catalog-gen check` plus the ten checks make drift and policy breaches fail locally. Four things in `docs/architecture/` are wrong or under-specified against EventCatalog 4.12.3 and ODCS v3.0.2 and need changing before day one; none of them threatens the design. The catalog model follows the ADR-021 topology proposed from Spikes B and D (Classic domain bus → one forward hop → Custom central bus → per-consumer subscriber), which the catalog expresses as one straight-line chain of logical channels per event. Details and the exact doc edits are under *Recommended changes*.

Reproduce green (from `spikes/A-catalog-source-of-truth/`, Node 22 via `.mise.toml`, uv, task):

```sh
task catalog:install
task all        # gen → gen:check → checks → spectral → odcs:lint → test (28 passed) → catalog:build:clean (104 pages, tree clean)
task gen:explain -- catalog/events/OrderPlaced/odcs.yaml
```

## EventCatalog (version: core 4.12.3, create-eventcatalog 4.3.13, Node 22.x)

| Capability | Renders? | How | Note |
| --- | --- | --- | --- |
| OpenAPI via `specifications` | Yes | `specifications: [{type: openapi, path: openapi.yaml, name: ...}]` on the service; spec page at `/docs/services/order-service/1.0.0/spec/openapi` with EventCatalog's own viewer | The object form `openapiPath:` is legacy. `x-eventcatalog-message-type` survives into the embedded spec but core does not read it. |

| anything resembling data products / containers | Partly | `data-products/<id>/index.mdx` with `inputs[] {id, type: event}` and `outputs[] {id, type: container, contract: {path, name, type}}`; domains link them via `data-products:`; the page builds and the domain page lists it | `outputs[].contract` is **not surfaced** in the static HTML (neither name nor content). Other facts about 4.12.3 that shaped the spike:

- **Unknown top-level frontmatter keys fail the build.** `visibility`, `audience`, `source` as written in `conventions.md`/`generation-and-ci.md` cannot be used; they must be `x-visibility`, `x-audience`, `x-source` (any `x-*` is allowed and renders with `<CustomProperties />`). Nested unknown keys are silently dropped.
- **The build mutates source files.** A "Channels migrated to new services API" step rewrites message-level `channels:` into the services' `sends[].to` / `receives[].from`, reflows `summary` to `>-` and quotes URLs. It also guessed wrong: it put the *event's* channels on the receiver's `from`, so payment-service "received OrderPlaced from orders-bus" — the opposite of fan-out. Author the canonical form (channels on the sending service), and make CI fail on a dirty tree after build (`task catalog:build:clean`; the workflow does the same).
- **Channel chains are first-class; the physical hub overflows; per-event logical channels fix it.** A channel's `routes: [{id}]` declares that it forwards to another channel and the graph draws the chain. Declaring the *physical* ADR-001 topology (orders-bus → central-bus, payments-bus → central-bus, central-bus → both) makes `eventcatalog build` fail with `RangeError: Maximum call stack size exceeded` while rendering the event pages; with central routing back to only one spoke it builds, so the trigger is a hub routing back to two or more buses that route into it (worth an upstream issue). The fix that also matches ADR-021 (proposed from Spikes B and D): **one logical channel per event per physical bus**, generated by `catalog-gen` — `orders-bus.OrderPlaced.v1` → `central-bus.OrderPlaced.v1` → `payments-sub.OrderPlaced.v1` → payment-service. Every event's path is a straight line, so there is no cycle at all; the routes are the generated forward rule and subscriber one-for-one, including the fact that a domain never receives its own public event back; and there are no standalone bus pages at all: the physical bus is a name (`x-bus` on the domain, `x-physical-channel` on each logical channel), not a node, so nothing can ever route into a hub. The site builds with 7 generated channel pages; `check` covers them like the ODCS files (marker `x-generated: catalog-gen`).
- **Node ≥ 22.12 is required** (Astro). The repo's `.mise.toml` pins Node 20 and the spike README said 18+; the first build failed. `spikes/A-catalog-source-of-truth/.mise.toml` pins 22 for this directory.
- `versioned/<v>/` holds *previous* versions; the current version lives at `events/<Event>/index.mdx`. `data-contracts.md` says the contract lives at `events/<Event>/versioned/<v>/odcs.yaml`; the current contract lives at `events/<Event>/odcs.yaml`, and moves under `versioned/` with the rest of the event when a new version lands.
- **Relative `$ref`s break under `versioned/`.** When an event version is retired to `events/<E>/versioned/<v>/`, its schema sits two directories deeper and `../../schemas/Money.json` no longer resolves (found by the two-version test). Rule adopted: **event schemas reference shared schemas by `$id` URL** (`https://platform.example/schemas/Money.json`); **shared schemas and the OpenAPI reference each other relatively**, because they never move and because Spectral resolves relative refs itself but would try to fetch an `$id` URL over the network. The generator and the checks resolve `$ref` through a registry of every `schemas/**/*.json` `$id` first and fall back to a relative path.
- `examples/*.json` beside `index.mdx` renders an Examples tab and copies the files into `dist/` — no frontmatter needed. The spike's examples are full EventBridge envelopes and double as fixtures for `check_examples_match_schema`.
- `sunset` is not a frontmatter key; the lifecycle fields are `draft` and `deprecated: {date, message}`.
- Scaffold: `npx @eventcatalog/create-eventcatalog@4.3.13 catalog --organization-name Platform --empty --use-npm` with `n` piped to the one prompt (install skills). `--empty` avoids the demo content.
- `.astro/` is the build cache (add to `.gitignore`); output is `dist/`; 104 pages for this catalog in ~9 s; the built-in link validator runs on every build.
- `CODEOWNERS` inside `catalog/` is content only — GitHub reads the repo root (or `.github/`, `docs/`). Fine while the catalog is its own repo on day one; otherwise generate the root file from the catalog's.

## Generator

- **Overlay merge rule on conflicts: strict ownership, fail on conflict.** The overlay (`data-product.yaml`) may *replace* `description`, `slaProperties`, `team`, `terms`, `support`, `price`, `tags`; may *append* to `quality` and `authoritativeDefinitions`; and may *add* `customProperties` by name, with the generated value winning on a clash. Any other key (`id`, `schema`, `servers`, `roles`, `status`...) aborts the build with "overlay may not set generated keys [...]; change the event schema instead". `test_overlay_may_not_set_generated_keys` proves it. Nothing merges silently, so a reviewer only ever sees overlay-owned keys in a `data-product.yaml` diff.
- **Pattern-size reality with 12 public events:** the forward pattern for 11 orders events is 326 bytes compact; the fan-out pattern is a constant 50 bytes; the enumerated alternative is 35 bytes per other domain (2.4 KB at 100 domains). Neither fan-out form depends on the number of events, so the 4 KB risk is only in the forward pattern, at roughly 150 events per domain with ~24-character names. The generator splits the forward pattern into `-part-N` files at `--pattern-limit` (default 4096) and lists the parts in `deploy-order.json`; `test_generator_splits_forward_pattern_at_the_limit` forces a split at 160 bytes and checks each part is under the limit, shares the `source` prefix, and that the parts' union equals the unsplit list in order. Recommendation: keep `anything-but` as the deployed fan-out form; emit the enumerated form only as documentation.
- **Validation bundle:** direct fields of public events are rewritten to the ciphertext-envelope schema (`{enc: v1, kid, ct}`) regardless of their logical type, so Firehose rejects clear text by schema alone — `test_validation_bundle_accepts_examples_and_rejects_clear_text_direct`. Composing `Envelope` with a payload via `allOf` **does not work** when the payload has `additionalProperties: false` (the envelope keys become "additional"); the generator flattens envelope + payload into one closed object and fails on a field-name collision.
- **ODCS written into the catalog** beside the event (committed, `# GENERATED` header), because that is the only place EventCatalog can render it and the only way a PR shows the contract diff. `check` covers it; a stray or edited `odcs.yaml` is a drift failure like any file under `generated/`.
- **Money flattening:** `d_<field>` `decimal128(18,4)` plus `d_<field>_currency` — `data-contracts.md`'s `d_currency` is ambiguous as soon as an event carries two Money fields.
- **Subscriptions (ADR-021):** each (consuming domain, event name) is one subscription; received versions collapse into the `detail-type` list; targets (services) are recorded in the manifest's `consumers` map so two services in one domain share one subscription. A *same-domain* subscription is a consumer rule on the domain bus (`rules/{d}-consumer-{event}.json`); a *cross-domain* one is a **subscriber on central** (`subscribers/{d}-{event}.json`: filter = the same Classic pattern, retry 185 attempts / 86 400 s, DLQ, `maxBatchSize` 1, targets) — the artefact ADR-021 says the generator must emit, and the Classic pattern is reused verbatim as the subscriber's DATA filter. Commands and queries in `receives[]` are API operations and produce nothing. A `receives[]` for an unknown event yields a detail-type-only subscriber and is flagged by `check_receives_target_public_or_same_domain`. Fan-out rules are still emitted but only as the platform-local Classic stub.
- **Logical channel pages:** `emit_channels` writes `channels/{bus}.{dt}/index.mdx` for every event, `channels/central-bus.{dt}/` for public ones (routes to each consuming domain's subscriber channel) and `channels/{domain}-sub.{dt}/` per subscriber, with `address` (the physical ARN template), `x-physical-channel`, `x-detail-type`, `x-source`, `x-filter`/`x-retry-policy` where relevant, and `<ChannelInformation />`. Services reference these ids in `sends[].to` / `receives[].from`; `test_logical_channels_form_a_straight_line_per_event` asserts the chain and that no physical channel is a route source or target.
- **Routing map** carries `detailTypes` per source prefix (not just the bucket), so flipping an event's visibility changes it, as the spike prompt expects; the Firehose dynamic-partitioning config needs the list anyway.
- **Exact change sets** (both tests assert equality, not superset): flipping `order.aggregate.updated` to public changes `rules/orders-public-forward.json`, `archive/routing-map.json`, `validation/orders.json`, `parquet/order.aggregate.updated.v1.json`, `catalog/events/order.aggregate.updated/odcs.yaml`, `deploy-order.json`, nothing in payments. Adding a `receives[]` changes `rules/payments-consumer-customer-registered.json` and `deploy-order.json` only.
- **Explain** prints the emitter and the catalog files whose change would alter the generated file (provenance collected while emitting), e.g. the ODCS for OrderPlaced ← `events/OrderPlaced/{index.mdx,schema.json,data-product.yaml}`, `schemas/Money.json`, `domains/orders/index.mdx`.
- **Awkward parts of `generation-and-ci.md`:**
  - It names catalog fields `visibility`, `audience`, `pii` that EventCatalog will not accept unprefixed (see above).
  - "Firehose validation schema bundles" is one line; the envelope composition and the ciphertext substitution are where the design actually lives and should be written down.
  - "entities are not in the shared root" never defines *entity*. The spike uses `x-kind: entity` or a property named `<Name>Id` as the identity heuristic; `schemas/Money.json`, `Address.json`, `Envelope.json` are value objects at the root, `schemas/orders/Order.json` is the entity.
  - "Schema diff ... against main" needs a base checkout; locally there is none. `run_checks.py --base <dir>` is optional and the workflow adds a worktree of the base ref.
  - "`sunset` enforcement data": no such field exists; map to `deprecated.date`.
  - Command/query pages: the doc assumes they come "from `services/*/openapi.yaml`" — in core they do not. Either the day-one generator emits `commands/` and `queries/` pages from the OpenAPI (recommended; trivial given the check already parses the spec) or the platform pays for Scale.
  - The ODCS example is not valid ODCS v3.0.2: `logicalType: timestamp` is not in the enum (`string|date|number|integer|object|array|boolean`; timestamps are `date`), and `schema[].name` is required. `fixtures/odcs/bad.odcs.yaml` reproduces the two failures with `datacontract lint`.

## Checks that were hard to express
- **"Commands are POST" in Spectral.** A JSONPath filter `[?(@['x-eventcatalog-message-type']=='command')]` after `[get,put,...]` descends into the operation's *children*, so the rule never fired; the working form is `given: $.paths[*][get,put,patch,delete]` and `then: {field: x-eventcatalog-message-type, function: pattern, notMatch: ^command$}`. The slow test caught it.
- **`x-pii` on `$ref` properties in OpenAPI.** With `resolved: true` (the default) Spectral replaces the `$ref` node and drops sibling keys, so the rule reported `Money.json` as missing `x-pii`; `resolved: false` fixes it. The same sibling-keys-on-`$ref` convention is what the generator relies on (`total: {$ref: Money, x-pii: none}`), and it is legal in 2020-12.
- **Recursive meta-schema.** The starter meta-schema only looked at top-level properties. Recursion via `$defs/property` works, but `not: {properties: {x-pii: {const: special}}}` only bites if `required: [x-pii]` is inside the `not`, otherwise an absent key satisfies the `not`.
- **Sync-hop depth.** EventCatalog has no "calls" relation; the graph has to be rebuilt from commands/queries (caller `sends`, provider `receives`). It needs the operation pages to exist, which is another reason to generate them.
- **Bus topology.** The first cut put `central-bus` in the publisher's `sends[].to`, which rendered as direct publishing to central and hid the second hop; a reviewer spotted it. Physical channels with `routes` reproduce the hub and overflow the renderer (above). The settled model is per-event logical channels, and `check_channel_topology` enforces their use: a service `sends` an event only to `{own-bus}.{detail-type}`, receives a same-domain event from that channel and a cross-domain event only from `{own-domain}-sub.{detail-type}`, for exactly the versions it names (`latest`, `1.0.0` and `^1.0.0` resolve the same way in the check and the generator; a version that matches nothing fails both), and never names a bare bus. Visibility stays an explicit per-event key (`x-visibility`); the generator turns it into the presence of the `central-bus.{dt}` channel and the route to it.
- **Entity at the shared root** is a heuristic; worth an explicit `x-kind` requirement on every file under `schemas/`.
- **Schema diff** is a hand-rolled breaking-change detector (removed property, type/format change, newly required, narrowed enum, tightened `additionalProperties`). It is enough for the spike; day one should evaluate `json-schema-diff` or `oasdiff` rather than grow this.

## Recommended changes to roadmap / ADRs
1. **`conventions.md`, `generation-and-ci.md`:** rename the catalog fields to `x-visibility`, `x-audience`, `x-source`; state the channel model — channels are logical and per event (`{bus}.{detail-type}`, `central-bus.{detail-type}`, `{domain}-sub.{detail-type}`), generated from `sends`/`receives`/visibility; a service `sends[].to` its own bus's channel for the event and `receives[].from` its own subscriber channel (or its own bus's channel for same-domain events); buses are names (`x-bus`, `x-physical-channel`), not channel pages — and that CI fails when `eventcatalog build` rewrites the tree. Visibility stays an explicit per-event key; the generator renders it as the route to central.
2. **`data-contracts.md`:** contract path `events/<Event>/odcs.yaml` (current version); `logicalType: date` for timestamps; `schema[].name` required; `d_<field>_currency` for Money; add the overlay ownership rule above verbatim (it is the answer to "how should the overlay merge behave on conflicts").
3. **Step 2 (generator) scope:** add emitting `commands/` and `queries/` pages from OpenAPI (`operationId` → page id, `x-eventcatalog-message-type` → folder) so core EventCatalog suffices without a Scale licence; add emitting the per-event logical channel pages and, per ADR-021, one **subscriber** definition per cross-domain `receives[]` (filter = the Classic consumer pattern, retry 185/24 h, DLQ, target) in place of fan-out rules and cross-domain consumer rules; keep the fan-out pattern only as the platform-local Classic stub; add "ODCS and channel pages written into the catalog and committed; `check` covers them" and "forward pattern split at 4 KB".
4. **Toolchain:** Node 22 in `.mise.toml` (repo-wide, or per catalog directory as here); `.astro/` in `.gitignore`.
5. **`pii.md` / ADR-007:** `x-pii` is a JSON Schema keyword on every property, including shared `schemas/`; frontmatter carries nothing but a derived badge. State that direct fields of public events are *schema-typed as the ciphertext envelope* in the generated validation bundle, which is how Firehose quarantines clear text without code.
6. **ADR-017:** add two sentences — the catalog build must be idempotent on its sources (CI diff gate), and `CODEOWNERS` is generated to the repo root from the catalog's per-domain file when the catalog shares a repo.
7. **Testing:** keep the golden snapshot in `tests/golden/` (since `generated/` is gitignored) and the per-check fixture overlay pattern (`fixtures/checks/<check>/` copied over a clean catalog); both were cheap and caught real bugs (the `allOf` composition, the Spectral filter).

## What differed from `docs/architecture/`, in one list
- Frontmatter keys need `x-` (README glossary, conventions.md, generation-and-ci.md).
- Current-version paths, not `versioned/` (data-contracts.md).
- ODCS `logicalType` enum and required `schema[].name` (data-contracts.md example).
- `d_currency` → `d_<field>_currency` (data-contracts.md, data-layer.md).
- Command/query pages are not derived by core EventCatalog (README end state, generation-and-ci.md).
- `sunset` is not an EventCatalog field (conventions.md, generation-and-ci.md).
- Node 22, not 18/20 (spike README, .mise.toml).
- The build rewrites the source tree (not mentioned anywhere; it must be).
- `allOf` cannot compose envelope + closed payload (implicit in generation-and-ci.md's "validation schema bundles").

## Recommendation
Proceed to day one with the changes above folded into `conventions.md`, `data-contracts.md`, `generation-and-ci.md` and the step-2 generator scope before the day-one prompts run. The load-bearing claim held: every routing pattern, validation schema, Parquet schema, PII rule and data contract in this spike is a deterministic function of the catalog, `check` fails on a one-character edit anywhere, and the ten checks each fail on their own fixture and pass on the clean catalog. The costs discovered are conventions, not architecture: `x-` prefixes, channels on the sender, a Node bump, a build-idempotency gate, and generating the command/query pages ourselves. Spike C can take `generated/local/rules/*.json`, `validation/*.json` and `archive/routing-map.json` as they are.
